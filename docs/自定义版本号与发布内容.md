# 自定义版本号与发布内容

1.2.0 新增在线下载安装，发布附件要求见 [一键在线更新](./一键在线更新.md)。版本号仍按下方三处同步修改。

根据当前本地 **1.1.1** 源码核对，核对日期：2026-10-03。
本文以计划发布 **1.2.0** 为例，仅说明修改流程；没有替你修改实际版本或发布 GitHub Release。

## 一、先分清三件事

- **插件版本**：由源码的三个版本字段共同定义，决定安装后显示的版本。
- **远端更新版本**：当前更新器读取 GitHub Release 的 `tag_name`，再与插件版本比较。
- **更新内容**：本地写入 `CHANGELOG.md`，GitHub 上写入 Release 说明；当前插件面板没有展示 Release 正文的功能。

只修改 ZIP 文件名、Release 标题或 README，不会改变 ZIP 内部插件版本。

## 二、编辑哪个目录

日常维护使用源码根目录：

```text
E:\mapper\Unpackaging tool\unityUnpackaging tool\blender插件
```

`GitHub发布_1.1.1` 是当时交付的独立副本，不会自动随根目录源码变化。
不要只改这份副本，却运行根目录的打包脚本。下面的步骤统一在根目录源码上操作。
先保留工作副本或 Git 提交，避免覆盖已经发布的旧版包。

## 三、修改插件版本号：三处保持一致

### 1. 传统插件入口

文件：

```text
E:\mapper\Unpackaging tool\unityUnpackaging tool\blender插件\bomberstudio_blender\__init__.py
```

在 `bl_info` 中将这一项改为目标版本：

```python
'version': (1, 2, 0),
```

这里用数字元组，不要写成字符串 `'1.2.0'`。

### 2. 面板、比较和打包使用的版本

文件：

```text
E:\mapper\Unpackaging tool\unityUnpackaging tool\blender插件\bomberstudio_blender\core.py
```

修改：

```python
VERSION = (1, 2, 0)
```

面板的“当前版本”、更新比较和打包 ZIP 名称都读取它。

### 3. 扩展清单

文件：

```text
E:\mapper\Unpackaging tool\unityUnpackaging tool\blender插件\bomberstudio_blender\blender_manifest.toml
```

修改：

```toml
version = "1.2.0"
```

这里只改插件的 `version`。`schema_version`、`blender_version_min`、`bl_info['blender']`
不是本插件版本，不要一起替换。内置 Source Tools 的 `3.4.3` 是第三方组件版本，也不随主插件版本修改。

建议以三段数字递增：小修复 `1.1.2`、新增功能 `1.2.0`、较大改动 `2.0.0`。
正式更新使用 `v1.2.0` 这类 Tag；当前比较器没有对 `v1.2.0-beta.1` 实现预发布版本排序。

## 四、自定义更新内容

### 1. 本地更新日志

编辑：

```text
E:\mapper\Unpackaging tool\unityUnpackaging tool\blender插件\CHANGELOG.md
```

在旧记录前面插入新版本，不删除历史记录。示例结构如下，把占位说明替换成实际完成的内容：

```markdown
## 1.2.0 — 发布日期

### 新增
- 填写本次实际新增的功能。

### 修复
- 填写已修复的问题及受影响的场景。

### 使用说明
- 填写升级后需要注意的操作；没有变化时可以省略。
```

打包脚本会把根目录这份更新日志放入 ZIP，但不会自动把它提交到 GitHub Release。

### 2. GitHub 的标题与说明

发布时让内容对应同一版本：

| 字段 | 示例或填写方式 | 本插件是否读取 |
|---|---|---|
| Tag | `v1.2.0` | 是，读取 `tag_name` 比较版本 |
| Release 标题 | `BomberStudio Blender 1.2.0 — 你的更新主题` | 当前未读取 |
| Release 正文 | 粘贴本次 `CHANGELOG.md` 对应小节，可自由编写 Markdown | 当前未读取 |
| Assets 附件 | 新构建的 `BomberStudio_Blender_1.2.0_Universal.zip` 和 `SHA256SUMS.txt` | 1.2.0 起可在确认后自动下载、校验并安装 |

`BomberStudio_Blender_1.2.0` 这种以三段版本号结尾的 Tag 也已适配；建议固定使用一种命名规则。
**Release 标题可以自定义，但不要用改标题的方式代替改 Tag。**
当前更新器请求 `/releases/latest`，没有查询草稿或预发布版本列表；发布正式版后再从插件手动检查。

### 3. 仓库首页和安装说明

编辑以下文件的当前版本说明、下载文件名和链接，使其与新包一致：

```text
E:\mapper\Unpackaging tool\unityUnpackaging tool\blender插件\README.md
E:\mapper\Unpackaging tool\unityUnpackaging tool\blender插件\docs\使用指南.md
E:\mapper\Unpackaging tool\unityUnpackaging tool\blender插件\docs\GitHub发布步骤.md
```

历史更新记录和历史测试报告中的旧版本应保留，不要对全项目执行无差别替换。
已验证 1.1.1 的测试报告不应只改标题就充当 1.2.0 的测试结果。

## 七、上传时保持同一批源码与附件

1. 上传这次修改后的根目录源码、文档和测试文件，不要上传旧发布目录中的文件冒充新版本。
2. 如果 README 使用仓库根目录的相对 ZIP 链接，根目录也要上传对应的新 ZIP。
3. 提交完成后创建对应版本的正式 Release，Tag 关联本次源码提交。
4. 上传本次新包与配套 `SHA256SUMS.txt`，填写更新说明，再发布。
5. 用插件的手动检查确认远端版本；本地版本相同应显示相同，本地旧版应提示更新。
6. 更新内容只改措辞时可编辑说明；插件代码有变化时建议递增版本并重新构建、测试，不悄悄覆盖旧包。

最终应对应：**源码三处版本 = ZIP 内部版本 = 文件名版本 = Release Tag 数字版本**。

## 八、你可能看到的现象

- ZIP 名称是 1.2.0，面板仍显示 1.1.1：只重命名了旧包、没有重启，或正在启用另一份插件。
- GitHub 标题是 1.2.0，检查仍显示 1.1.1：更新器读取的是 Tag，而不是标题；还应检查请求返回的是哪条正式 Release。
- 更新说明写好了，插件里看不到全文：当前面板只显示版本状态，正文要在发布页查看。
- 测试报版本不一致：核对 `__init__.py`、`core.py`、`blender_manifest.toml`，不要只改一个。
- 源码修改了，发布目录没变化：打包脚本不负责同步历史发布目录，上传时应使用本次实际源码和新包。
